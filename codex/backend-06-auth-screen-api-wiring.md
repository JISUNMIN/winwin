# Backend 06. Auth 화면과 실제 API 연결

## 이번 단계 한 줄 요약

이번 단계에서는 `/auth` 화면에 실제 로그인/회원가입 폼을 붙이고,
성공 시 auth API 응답을 세션 provider에 저장하도록 연결했습니다.

즉 지금 상태는:

```text
역할 선택만 하던 mock auth 화면
-> 실제 auth API를 호출하는 로그인/회원가입 화면
```

입니다.

## 이번 단계에서 바꾼 핵심

수정 파일:

- [src/app/auth/index.tsx](/abs/path/C:/Users/zentropy/Music/WinWin/WinWin/src/app/auth/index.tsx)

이번 단계의 핵심은 아래 4가지입니다.

### 1. `/auth` 화면에 로그인 / 회원가입 모드 추가

기존에는 `게스트 / 고객 / 파트너` 역할 카드만 있었습니다.

이번에는:

- `로그인`
- `회원가입`

두 모드를 전환할 수 있도록 바꿨습니다.

즉 이제 `/auth` 화면은:

```text
로그인 탭
회원가입 탭
게스트 / mock 빠른 전환 영역
```

으로 나뉘어 있습니다.

### 2. 실제 auth API 호출 연결

현재 연결한 API:

- `login(...)`
- `signup(...)`

즉 사용자가 입력한:

- 이메일
- 비밀번호
- 이름
- 회원가입 역할(customer / partner)

을 가지고 실제 Spring auth API를 호출합니다.

### 3. 성공 시 `completeAuthSession()`으로 세션 저장

로그인/회원가입이 성공하면
이전 단계에서 준비한 provider 함수:

```text
completeAuthSession(...)
```

을 호출해서 아래를 저장합니다.

- access token
- user id
- email
- name
- role

즉:

```text
API 성공 응답
-> auth provider 세션 저장
-> 로그인 상태 반영
-> 권한에 맞는 화면으로 이동
```

흐름이 실제로 연결된 것입니다.

### 4. validation / conflict / auth 에러 표시

이전 `backend-03`에서 정리한 백엔드 에러 응답 구조를
현재 auth 화면에서 바로 활용하도록 붙였습니다.

예를 들면:

- 이메일 형식 오류
- 비밀번호 길이 부족
- 이름 공백
- 이미 가입된 이메일
- 잘못된 로그인 정보

같은 경우에 에러 메시지를 화면에 표시할 수 있습니다.

특히 validation 에러는:

```text
fieldErrors
```

를 이용해 입력 필드별로 보여주도록 연결했습니다.

## 현재 `/auth` 화면 구조

지금 화면은 크게 아래처럼 이해하면 됩니다.

### 1. 상단 안내

- 현재 접근하려는 화면이 특정 권한을 요구하는지 표시
- 예: 고객 권한 필요 / 파트너 권한 필요

### 2. 현재 로그인 상태 카드

- 현재 role
- mock 세션인지 api 세션인지
- API 세션이면 현재 user email

을 보여줍니다.

### 3. 실제 로그인 / 회원가입 폼

로그인:

- 이메일
- 비밀번호

회원가입:

- 이메일
- 이름
- 비밀번호
- 고객/파트너 역할 선택

### 4. 게스트 / 개발용 빠른 전환

현재 프로젝트는 아직 auth 이행 중이라
기존 mock 빠른 전환도 같이 유지했습니다.

즉:

- 게스트
- 고객 mock
- 파트너 mock

버튼도 계속 남겨두었습니다.

## 왜 mock 빠른 전환을 아직 지우지 않았나

지금은 실제 auth API 연결을 시작하는 단계이지만,
앱 전체 화면 흐름은 아직 mock 전환을 많이 쓰고 있습니다.

예:

- 홈 상단 role 전환
- 고객/파트너 화면 테스트
- 보호 라우트 흐름 점검

그래서 이번 단계에서는
실제 auth 화면을 붙이되,
기존 mock 빠른 전환도 같이 남겨두는 쪽이 더 안전합니다.

즉 지금은:

```text
실제 auth API 연결 시작
동시에
개발용 mock 전환 유지
```

전략으로 가고 있습니다.

## 권한 불일치 처리

예를 들어:

- 고객 전용 화면에 들어가려 했는데
- 파트너 계정으로 로그인한 경우

에는 로그인 자체는 성공시키고,
요청한 화면 대신 해당 role의 기본 화면으로 보내도록 처리했습니다.

즉:

```text
로그인은 성공
-> 하지만 요청 권한과 다르면
-> 그 role 기본 화면으로 이동
```

하도록 했습니다.

## 이번 단계에서 아직 하지 않은 것

이번 단계에서는 아래는 아직 남아 있습니다.

- 홈 상단 mock 역할 버튼을 실제 auth 기준으로 정리
- 회원가입/로그인 성공 후 성공 메시지 UI 다듬기
- 로그인 유지 만료 시 전역 `401` 처리 정리
- `/auth` 화면 디자인을 더 제품형으로 다듬기

즉 이번 단계는 “기능 연결”이 중심이고,
디자인/정책 정리는 아직 후순위입니다.

## 다음 단계

다음 작업은 아래 순서가 자연스럽습니다.

### 1. 홈 상단 mock 전환 버튼 정리

현재 홈 상단에는 아직 `게스트 / 고객 / 파트너` 빠른 전환 버튼이 있습니다.

다음에는:

- 개발용 라벨을 붙일지
- 숨길지
- 실제 로그인 상태 중심으로 단순화할지

를 정해야 합니다.

### 2. `401` 공통 처리 보강

앱 시작 시 세션 복원에서만 아니라,
일반 API 요청 중 `401`이 나는 경우에도
세션 정리와 `/auth` 이동 기준을 맞추는 작업이 필요합니다.

### 3. post API 연결 시작

auth 기반이 어느 정도 잡혔으니,
다음 큰 축은 공고 목록/상세를 실제 API로 바꾸는 작업입니다.

이 시점부터는 React Query 도입 검토 가치도 점점 커집니다.
