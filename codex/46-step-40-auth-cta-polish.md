# 46. WinWin 프로젝트 목표 정리

## 이 문서를 만든 이유

지금까지는 화면과 흐름을 하나씩 구현하면서 step 문서 위주로 기록했습니다.

이제부터는:

- 이 프로젝트를 어디까지 만들 것인지
- 무엇이 1차 목표인지
- 무엇이 나중 고도화 대상인지
- Google Play 배포까지 보려면 무엇을 완료해야 하는지

를 기준으로 방향을 다시 잡을 필요가 있어서, 프로젝트 목표 문서로 정리합니다.

## 프로젝트 한 줄 목표

`WinWin`은 고객과 파트너를 연결하는 매칭 앱을 React Native로 구현하고, mock 단계에서 끝내지 않고 실제 인증/API를 붙인 뒤 Google Play에 배포 가능한 수준까지 완성하는 것을 목표로 합니다.

## 이 프로젝트로 얻고 싶은 것

이번 프로젝트의 핵심 가치는 단순 UI 제작이 아닙니다.

이번 프로젝트를 통해:

- RN/Expo 기반 모바일 앱 구조 이해
- 고객/파트너 역할이 있는 앱 흐름 설계
- 보호 화면, 인증, 마지막 화면 복구 같은 앱 상태 관리 경험
- mock 데이터를 실제 API로 교체하는 경험
- Android 릴리즈 빌드와 Google Play 배포 경험
- 포트폴리오에서 설명 가능한 end-to-end 앱 제작 경험

까지 가져가는 것이 목표입니다.

## 1차 목표

### 1. 앱 흐름 완성

최소한 아래 사용자 흐름이 실제 앱처럼 이어져야 합니다.

- 게스트가 홈과 상세 화면을 본다
- 고객이 로그인 후 공고를 보고 상담을 시작한다
- 고객이 희망 일정을 보내고 예약 요청/결제 흐름을 확인한다
- 파트너가 로그인 후 상담 목록과 채팅을 본다
- 파트너가 공고를 등록, 수정, 마감 처리한다

### 2. mock 제거

현재 구조는 학습과 화면 검증에는 충분하지만, 실제 서비스처럼 동작하지 않는 부분이 남아 있습니다.

1차 목표에서는 아래를 실제화합니다.

- mock auth -> 실제 로그인/회원가입 API
- 메모리 공고 데이터 -> 실제 DB 저장
- mock 상담/채팅 상태 -> 실제 API 조회/저장

### 3. Android 배포 가능 상태 만들기

반드시 상용 서비스 수준까지 가지 않더라도, 최소한 Google Play에 올릴 수 있는 수준까지 만드는 것이 중요합니다.

즉:

- release 빌드 가능
- 앱 정보/아이콘/환경 분리 정리
- 정책상 필요한 정보 준비
- 테스트 트랙 업로드 가능

상태까지 가는 것을 1차 완성으로 봅니다.

## 이 프로젝트에서 중요한 우선순위

### 가장 중요한 것

- 실제 앱처럼 이어지는 핵심 사용자 흐름
- 인증/권한/상태 관리 구조
- API/DB 연동 경험
- 배포 가능한 상태까지 마무리

### 지금 당장 우선순위가 아닌 것

- 세세한 UI 고도화
- 과한 애니메이션
- 일부 부가 기능 추가
- 초기 광고 수익화

즉 지금 단계에서는 `더 많은 기능`보다 `실제로 동작하는 최소 제품`에 가까워지는 것이 더 중요합니다.

다만 이것은 고도화를 하지 않는다는 뜻은 아닙니다.

현재 판단은:

- 서비스 고도화는 나중에도 계속 진행한다
- 하지만 지금은 백엔드, DB, API, 로그인/회원가입을 먼저 만든다
- 그 이후 누락된 기능과 backlog 항목을 다시 이어서 구현한다

프론트 개발도 아직 끝난 것이 아닙니다.

현재 의미는:

- 프론트에서 추가로 만들 기능이 더 남아 있다
- 다만 지금은 프론트 확장보다 DB와 API를 먼저 만든다
- 실제 데이터가 붙은 뒤 필요한 프론트 작업을 다시 이어서 진행한다
- 즉 프론트를 안 하는 것이 아니라, 우선순위를 백엔드 쪽으로 잠시 앞당긴 상태다

는 우선순위 정리입니다.

## 현재 프로젝트 상태 평가

지금까지는 아래가 이미 확보됐습니다.

- 홈, 상세, 채팅, 파트너 상담/공고 관리 흐름
- 고객/파트너 역할 분리
- mock 인증과 역할 가드
- auth 상태 저장
- 마지막 경로 복구
- 보호 화면 공용화

즉 UI와 앱 흐름의 뼈대는 이미 꽤 잘 올라와 있습니다.

반대로 아직 비어 있는 핵심은 아래입니다.

- 실제 회원가입/로그인
- 실제 사용자 정보
- 실제 공고 CRUD API
- 실제 채팅/상담 데이터 저장
- 실제 서버/DB
- 운영 환경 배포

## 기술 방향

현재 목표 기준으로는 `RN 앱 + Spring Boot 백엔드` 조합이 가장 적합합니다.

추천 방향:

- App: React Native + Expo
- Backend: Spring Boot
- Auth: Spring Security + JWT
- DB: PostgreSQL
- ORM: JPA
- Deploy: 초반 Render 또는 Railway, 이후 필요 시 AWS

현재 기준으로 이 프로젝트의 기본 조합은 `React Native + Expo + Spring Boot + Spring Security + JWT + PostgreSQL + JPA`입니다.

이렇게 가면:

- 모바일 앱 개발 경험
- 백엔드 구조 설계 경험
- REST API, DB 모델링, 인증/인가 경험
- Android 배포 경험

을 한 프로젝트 안에서 함께 설명할 수 있습니다.

## Google Play 배포 기준 목표

이 프로젝트는 나중에 실제 Google Play 배포까지 고려합니다.

여기서 중요한 점은 `상용 성공 여부`보다 `배포 가능한 앱을 끝까지 만들어 본 경험` 자체에도 충분한 가치가 있다는 점입니다.

이번 프로젝트에서 목표로 삼는 배포 수준은:

- Android 앱 서명/릴리즈 빌드
- Play Console 등록
- 내부 테스트 또는 비공개 테스트 배포
- 앱 설명, 아이콘, 스크린샷, 정책 항목 준비
- 리뷰어가 테스트 가능한 계정 제공

정도입니다.

이 수준만 가더라도 포트폴리오에서:

- 실제 출시 프로세스를 경험했다
- 코드 작성에서 끝나지 않고 배포까지 마쳤다
- 환경 분리와 운영 준비를 해봤다

고 설명할 수 있습니다.

## 서비스 고도화는 이후 단계에서 계속 진행

현재는 인증/API/DB가 먼저지만, 서비스 고도화 자체를 제외하는 것은 아닙니다.

백엔드 연동 이후에는 아래 작업도 계속 이어서 진행합니다.

- 현재 mock 기반으로 남아 있는 화면 흐름 실제화
- 누락된 액션과 상태 변경 연결
- 사용자 경험 개선
- 파트너/고객 화면 디테일 보완
- 운영 관점에서 필요한 예외 처리와 빈 상태 정리

즉 순서는:

```text
1. 백엔드와 인증 붙이기
2. 핵심 흐름을 실제 데이터로 전환
3. 누락 기능 보완
4. 서비스 고도화 진행
```

입니다.

## 수익화는 지금 목표가 아님

수익화는 나중에 검토할 수 있지만, 현재 우선순위는 아닙니다.

지금 단계에서는:

- 광고를 붙이기보다
- 앱 핵심 흐름을 실제화하고
- Play 배포가 가능한 상태까지 완성하는 것

이 더 중요합니다.

수익화는 이후에 아래 중 하나로 검토할 수 있습니다.

- 파트너 프리미엄 기능
- 공고 노출/매칭 수수료
- 예약/결제 연계 수수료
- 보조적 광고 도입

## 지금부터의 실전 목표

### 목표 A. 실제 서비스처럼 동작하게 만들기

- 회원가입/로그인 API
- 내 정보 조회
- 공고 목록/상세/등록/수정/마감 API
- 상담 목록/채팅 메시지 API

### 목표 B. Android 배포 가능한 품질 만들기

- mock 문구 줄이기
- 빈 화면/깨진 흐름 정리
- 앱 아이콘/이름/버전 정리
- production 환경 분리

### 목표 B-1. 누락 기능과 backlog 이어서 진행

기존 step 문서와 `progress-and-next-steps.md`에 남겨둔 항목도 백엔드 작업 이후 다시 이어서 진행합니다.

대표적으로:

- 실제 결제 연동 검토
- 사진 첨부 고도화
- 채팅/상담 상태 변경 연결
- 파트너 전용 화면 디테일 보완
- 공고 관리/상세 흐름 보완
- 역할별 진입 CTA와 auth 문구 다듬기

이런 항목들은 `없애는 일`이 아니라 `우선순위를 뒤로 미루는 일`에 가깝습니다.

### 목표 C. Google Play 테스트 배포

- 빌드
- 서명
- Play Console 업로드
- 테스트 계정/설명/정책 입력

## 당장 다음 우선순위

1. 실제 인증/API 구조 설계
2. Spring 백엔드 기본 프로젝트 시작
3. RN 앱에서 mock data 경계를 API client로 바꾸기
4. 공고/인증부터 실제 연동
5. Android 배포 준비 항목 정리

## backlog에 대한 원칙

현재 문서, step 기록, `progress-and-next-steps.md`에 적힌 나중 작업들은 살아 있는 backlog로 유지합니다.

정리하면:

- 이미 만든 기능의 뼈대는 유지한다
- 먼저 실제 백엔드와 인증으로 중심 축을 세운다
- 이후 backlog를 다시 꺼내 순서대로 마무리한다

즉 이번 프로젝트는:

- `백엔드/API 전환`
- `누락 기능 마감`
- `서비스 고도화`

를 순차적으로 모두 가져가는 방향입니다.

## React 개발자 기준으로 보면

이번 문서는 기능 구현 step이라기보다 제품 목표와 release scope를 정하는 단계입니다.

웹 React 기준으로 보면:

- `프로토타입`에서 `MVP`로 넘어가기 전 scope 정리
- mock state 기반 화면 작업에서 실제 API 단계로 넘어가기 전 경계 확인
- UI 작업 중심에서 배포 가능한 제품 기준으로 우선순위를 재설정

하는 단계와 비슷합니다.

즉 느낌상:

- 지금까지: interactive prototype
- 다음 단계: production-oriented MVP
- 최종 1차 목표: Play Store test release capable app
